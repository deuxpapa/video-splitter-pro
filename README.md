# Video Splitter Pro

大きい動画も、端末に丸ごと読み込まずに分割できるWebアプリです。
「かんたん動画分割」の後継版で、動画ファイルを少しずつ読み込みながら処理する方式に作り替えています。
Safariで開いて「ホーム画面に追加」すると、アプリのように使えます。

## 作られた経緯

前身の「かんたん動画分割」は、動画ファイルを丸ごと端末のメモリに読み込んでから処理する方式（ffmpeg.wasm使用）でした。実機検証で、337MBの動画は成功したものの、724MBの動画は分割ボタンを押してから約2秒でタブがクラッシュすることが確認され、「動画を丸ごと読み込む」という設計そのものが根本原因と判明しました。本アプリはこの制約を取り除くため、MP4/MOVコンテナを箱（box）単位で解析できる mp4box.js を使い、ファイルを少しずつ読み込みながら分割する方式で作り直しています。

## 特長

- 動画をどこにもアップロードしない（処理はすべて端末内のブラウザで完結）
- 動画ファイルを少しずつ（8MBずつ）読み込みながら処理するため、動画全体のサイズがメモリ使用量に直結しない
- 再エンコードをしない方式（ストリームコピー）なので、画質を落とさずに分割できる
- 巨大なエンジン（旧版はffmpeg.wasm、約9MB）を毎回読み込む必要がないため、処理が非常に高速（数秒程度）
- 各パーツの撮影日時は、分割した日ではなく元動画のファイル更新日時を引き継ぐ。写真アプリ内では、元動画の直後にパーツ1・2・3…の順で並ぶ

## 公開してiPhoneから使う方法（GitHub Pagesの手順）

このアプリはファイルを開くだけ（`file://`）では、写真の選択やホーム画面追加がうまく動かないことがあります。
無料で簡単な方法として、GitHub Pagesでの公開をおすすめします。パソコンの操作だけで完結し、コマンド入力は不要です。

### 手順1：GitHubのアカウントを用意する

すでにお持ちの場合はこの手順は飛ばしてください。お持ちでない場合は、[github.com](https://github.com/) の右上「Sign up」からアカウントを作成してください（無料）。

### 手順2：新しいリポジトリ（保存場所）を作る

1. GitHubにログインした状態で、右上の「＋」ボタン→「New repository」をクリックします。
2. 「Repository name」に、好きな名前を入力します（例：`video-splitter-pro`。半角英数字が無難です）。
3. 「Public」が選ばれていることを確認します（**Private（非公開）にすると、無料プランではPagesが使えません**。動画そのものはこのアプリの外に出ないので、コードだけが公開されても実害はほとんどありません）。
4. 「Add a README file」などのチェックは入れないままで構いません。
5. 「Create repository」をクリックします。

### 手順3：ファイル一式をアップロードする

1. 作成されたリポジトリの画面で、「Add file」→「Upload files」をクリックします。
2. パソコンでこのフォルダ（`0_VideoSplitterPro`）を開き、中に入っている**ファイルとフォルダをすべて選択**します（`index.html`、`style.css`、`app.js`、`manifest.json`、`sw.js`、`manual.html`、`README.md`、`icons` フォルダ）。
   - ※ `0_VideoSplitterPro` フォルダ自体ではなく、**その中身**を選ぶのがポイントです。
3. 選択した状態のまま、ブラウザの「Drag files here」の枠の中にドラッグ＆ドロップします（`icons` フォルダごとドロップすれば、中の画像も一緒にアップロードされます）。
4. 一覧に `index.html` などが表示されたことを確認し、下にスクロールして「Commit changes」（緑色のボタン）をクリックします。

### 手順4：GitHub Pagesを有効にする

1. リポジトリ画面の上部にある「Settings」タブをクリックします。
2. 左側のメニューから「Pages」をクリックします。
3. 「Build and deployment」の「Source」が「Deploy from a branch」になっていることを確認します。
4. 「Branch」のところで、`main`（または `master`）と `/ (root)` を選び、「Save」をクリックします。
5. 数分待つと、ページ上部に「Your site is live at `https://(ユーザー名).github.io/(リポジトリ名)/`」のように、公開されたURLが表示されます。

### 手順5：iPhoneで開いて、ホーム画面に追加する

1. iPhoneのSafariで、手順4で表示されたURL（`https://(ユーザー名).github.io/(リポジトリ名)/`）を開きます。
2. 画面下の「共有」ボタン（四角から矢印が上に伸びたアイコン）をタップします。
3. メニューを下にスクロールし、「ホーム画面に追加」をタップします。
4. 右上の「追加」をタップします。
5. ホーム画面に増えたアイコンをタップすれば、次回からアプリのように開けます。

### アップデートしたいとき

あとでファイルの内容を直したくなったら、同じリポジトリの画面でファイルを開き、鉛筆マーク（Edit）で編集して「Commit changes」するか、手順3と同じ要領で「Upload files」から上書きアップロードすれば、数分後に公開ページにも反映されます。

### 手元のパソコンで動作確認だけしたい場合

Node.jsが入っていれば、このフォルダで以下のコマンドを実行すると、パソコンのブラウザで確認できます（iPhoneの「ホーム画面に追加」を試すにはインターネット上への公開が必要です）。

```bash
npx serve .
```

## 技術メモ

- 動画の解析・分割は、外部ライブラリを使わず、MP4/MOVコンテナの箱（box）構造を自前で読み書きしています（経緯は後述）。動画ファイル全体を一度にメモリへ読み込む必要はありません
- まず`File.slice()`でftyp/moovの位置だけを探し（`app.js` の `locateFtypAndMoov`）、moovの生バイトを取得します。そこから、コーデック設定（stsd）・トラックの基本情報（tkhd/mdhd/hdlrなど）・全サンプルの位置情報（stts/stsz/stsc/stco/stss/cttsを自前で解析）を一度に読み取ります（`extractTrackTemplates`/`parseSampleTable`）。パーツごとの分割処理では、必要な範囲のサンプルの実データだけを、その都度`file.slice()`で直接読み込みます（`readSampleData`）。断片化（fMP4）は使わず、通常のカメラ動画と同じ「moovに直接サンプル位置の表（stbl）がある」古典的なMP4として、パーツごとに自前で組み立てます（`buildTrak`/`buildStbl`）。ストリームコピー（再エンコードなし）です
- 各パーツの撮影日時・長さは、全パーツで初期化セグメントを使い回している関係で、そのままだと元動画全体の値になってしまうため、`mvhd`/`tkhd`/`mdhd` ボックスを直接書き換えて補正しています（`app.js` の `patchMp4Metadata`。version 0の32bitフィールドのみ対応）
- 保存はWeb Share API（共有シート）経由です。「ビデオを保存」「"ファイル"に保存」などを明示的に選んでもらう方式のため、保存先が分からなくなりにくく、保存の成否も画面に反映されます。この機能が使えないブラウザ（PCのブラウザなど）では、従来のダウンロード方式に自動で切り替わります
- 対応ブラウザは最新のSafari（iPhone）を想定しています。PC版Chromeでも動作します
- 実機検証の結果、337MBの動画は成功（処理1秒）したものの、724MBの動画は進捗の途中でクラッシュすることが確認されました。原因は入力側ではなく**出力側**にありました。`splitVideo()` が、切り出した各パーツ（生のArrayBuffer、1パーツ最大113MB程度）を、動画全体の読み込みが完了するまで配列に溜め込んでから、まとめてBlob化していたため、大きい動画では結局「元動画とほぼ同じ量のデータ」が同時にメモリ上に存在してしまっていました。これを修正し、各パーツができた時点で即座に日時を書き換えてBlob化し、生のArrayBufferへの参照をすぐに手放すよう変更しました（`app.js` の `emitIfReady`）
- メモリ対策の後、実機で「8個に分割・保存はできるが、写真アプリでサムネイルが真っ黒＋クラウドマーク、再生が数秒で止まる、動画情報がどのパーツも元動画全体と同じ長さ（例：07:28）になる」という問題が発生しました。原因の1つ目は、mp4box.jsが出力する各断片（moof）の`tfdt`（その断片が元動画全体の中で何秒目にあたるかを示す値）が、パーツ単位でリセットされず元動画全体での絶対位置のまま出力されることでした。各パーツの先頭を0秒とみなすよう`tfdt`を補正する処理（`app.js` の `rebaseFragmentTimestamps`）を追加してサムネイル生成の問題は解消しましたが、動画の長さ表示と再生の途中停止は残りました
- 実際に保存されたファイルをさらにバイト単位で解析した結果、原因の2つ目として**編集リスト（`trak/edts/elst`）**が見つかりました。`mvhd`/`tkhd`/`mdhd`の長さは正しく書き換えていたものの、各トラックが「ムービー全体の中で何秒間再生されるか」を宣言する`elst`（edit list）だけは元動画全体の長さ（例：448秒）のまま残っていました。iPhoneはこちらを長さ・再生範囲として信頼するため、mvhd/tkhdを直しても動画情報の長さは元動画のまま表示され、実データが尽きた後もスクラバーだけ動き続け、音声も正しく再生されない、という症状につながっていました。`patchMp4Metadata`で`elst`の`segment_duration`もあわせて書き換えるよう修正しました
- ここまでの修正後もファイル自体は完全に正しい状態になったにもかかわらず、iPhoneの実機では同じ症状（動画情報の長さが元動画のまま・再生が数秒で止まる）が再現し続けました。原因は、mp4box.jsの断片化機能（`setSegmentOptions`/`onSegment`）が内部的に**必ず「1コマ（1サンプル）＝1個のmoof+mdat」という単位で断片を作る**仕様になっていたことでした（60秒の動画で1000個以上の小さな断片が連結される）。仕様上は正しいfMP4ですが、この特殊な構造がiPhoneの動画取り込み・再生処理とうまく噛み合わなかったと考えられます。mp4box.jsからは`setExtractionOptions`/`onSamples`で生のサンプル列だけを受け取り、パーツ1個分のサンプルをすべてまとめて「1個のmoof＋1個のmdat」として自前で組み立てる方式に変更しました（`app.js`の`buildMoofMdat`）。一般的な動画ファイルに近い、まとまった大きさの断片になり、パソコンのブラウザでの検証では実際に最後まで正しく再生できることを確認しています
- この修正後、実機では「実際に再生できる時間が5秒→60秒（パーツの実データ分）に伸びた」という改善は見られたものの、動画情報の長さ表示（元動画全体の長さのまま）とスクラバーの挙動は変わりませんでした。ファイル内の標準的なメタデータ（mvhd/tkhd/mdhd/elst）はすべて検証済みで正しいため、残る手がかりとして、各trakに残っていたカメラのメタデータ（レンズ情報・Appleの独自メーカーノートなど、全パーツで元動画から書き換えずコピーされたまま）を疑い、取り除いてみましたが、写真アプリ上でレンズ情報が表示されなくなったことは確認できたものの、症状は変わりませんでした
- 標準的なメタデータ・カメラメタデータのどちらも原因ではないと確定したため、残る可能性として**断片化MP4（fMP4）という形式自体**を疑いました。iPhoneのカメラ動画は本来この形式では保存されず、写真アプリへの「ビデオを保存」という取り込み経路がこの特殊な形式を正しく扱えていない可能性です。断片化をやめ、通常のカメラ動画と同じ古典的な構造（moovに直接サンプル位置の表がある、moof/mdatを使わない）でパーツを組み立て直す方式に変更しました（`app.js` の `buildTrak`/`buildStbl`/`locateFtypAndMoov`/`extractTrackTemplates`）。パソコンのブラウザでの検証では、通常のMP4ファイルと同じ`[ftyp, moov, mdat]`という構成になり、長さ・編集リストも正しく、実際に最後まで正しく再生できることを確認しています
- この修正で実機での動画情報の長さ表示・再生停止の問題は解消しました。ただし別の症状が2つ見つかりました。1つ目は、パーツ数が多い動画で結果画面の全プレビューを一度に読み込もうとすると、iPhoneのSafariがデコーダーのリソース不足で一部のプレビューを表示できなくなる（黒い画面＋斜線の三角マーク）こと。画面内に入ったプレビューだけ読み込み、画面外に出たら読み込みを解除する遅延読み込み（`IntersectionObserver`）で対応しました
- 2つ目は、長い動画（13分47秒・953MB）で進捗60%あたりにクラッシュしたこと。原因は、全パーツの完成を待ってから結果画面へ表示する作りのままだったため、未保存データが動画の長さに比例して積み上がっていたことでした。パーツができ次第すぐに結果画面へ表示・保存できるようにし、未保存のまま同時にメモリへ残せる合計サイズに上限（500MB）を設け、上限に達したら保存されるまで後続パーツの作成を一時停止するよう変更しました（`app.js` の `waitForCapacity`/`releaseCapacity`、`onSegmentReady`）。保存が終わったパーツはプレビュー動画をすぐ画面から消し、メモリを解放します
- この対策後も、保存を都度進めながら分割しても、7個目あたりでクラッシュすることが実機で確認されました。未保存データの量とは無関係に進行するにつれてクラッシュに近づいたため、**mp4box.js自身が、動画を読み進めるほど内部にデータを溜め込み続けている**ことを疑いました（このプロジェクトの一番最初、ffmpeg.wasm版の時点から棚上げにしていた懸念と同種のもの）。当初は「一定パーツごとにmp4box.jsのエンジンを作り直す」対策を検討しましたが、調査の結果、mp4box.jsのサンプル抽出は新しいインスタンスでは必ずサンプル0番から順番にしか取り出せない仕様のため、動画の後半になるほど「作り直した直後の再読み込み」自体が肥大化してしまい、根本的な解決にならないことが分かりました。そこで方針を変え、**mp4box.jsを使うのをやめました**。moovの中のサンプル位置の表（stco/stsz/stsc/stts/ctts/stss）を自前で解析し、パーツごとに必要なサンプルの実データだけを`file.slice()`で直接読み込む方式に書き換えました（`app.js` の `parseSampleTable`/`readSampleData`）。外部ライブラリの内部状態に依存しないため、動画を読み進めても内部にデータが溜まり続けることが原理的に起こらず、メモリ使用量は「今読んでいるパーツ1個分」にほぼ比例するようになりました
